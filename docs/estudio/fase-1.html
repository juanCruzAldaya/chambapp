1. ORM y SQLAlchemy 2.0

¿Qué es un ORM? Object-Relational Mapping: una capa que traduce filas de tablas ↔ objetos de Python. En vez de escribir SELECT * FROM usuarios WHERE id = 1 y parsear tuplas a mano, hacés db.get(Usuario, 1) y recibís un objeto Usuario. El ORM genera el SQL por vos, evita inyección (parametriza siempre) y te da tipos.

Modelos y columnas (estilo Mapped)

SQLAlchemy 2.0 introdujo una sintaxis declarativa basada en type hints. Cada modelo es una clase que hereda de una Base declarativa; cada atributo es un Mapped[tipo] mapeado a una columna con mapped_column().

backend/app/models/user.py (extracto)
class Usuario(Base):
    __tablename__ = "usuarios"

    id: Mapped[int] = mapped_column(primary_key=True)
    email: Mapped[str] = mapped_column(String(255), unique=True, index=True)
    password: Mapped[str] = mapped_column(String(255))  # hash bcrypt
    nombre: Mapped[str | None] = mapped_column(String(100))
    calificacion_promedio: Mapped[Decimal | None] = mapped_column(Numeric(3, 2))
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now()
    )

Puntos clave de ese fragmento:

  • Mapped[int] vs Mapped[str | None]: el tipo le dice a SQLAlchemy (y a tu editor) si la columna es NOT NULL o nullable. str | None ⇒ permite NULL.
  • String(255), Numeric(3, 2): el tipo de la columna en la base. Numeric(3,2) = hasta 3 dígitos, 2 decimales (ej. 4.75) — ideal para una calificación.
  • unique=True, index=True en email: no se repite y se busca rápido (login por email).
  • server_default=func.now(): el valor por defecto lo pone la base (no Python). Más confiable para timestamps.

Detalle fino: el campo se llama password pero guarda el hash, nunca la contraseña en texto. El comentario lo aclara. En la Fase 2 el schema de respuesta directamente no incluye este campo.

Relaciones entre tablas

El dominio tiene 10 tablas conectadas. Un Usuario es a la vez cliente (contrata, reseña) y profesional (publica servicios, tiene agenda). Eso se modela con relationship().

relación uno-a-muchos: Usuario → Servicios
# En Usuario (lado "uno"):
servicios: Mapped[list[Servicio]] = relationship(
    back_populates="profesional",
    foreign_keys="Servicio.profesional_id",
    cascade="all, delete-orphan",
)

# En Servicio (lado "muchos"):
profesional_id: Mapped[int] = mapped_column(ForeignKey("usuarios.id"))
profesional: Mapped[Usuario] = relationship(
    back_populates="servicios", foreign_keys=[profesional_id]
)
  • ForeignKey("usuarios.id") es la columna real en la base (la restricción). relationship() es la comodidad de Python: te deja navegar servicio.profesional o usuario.servicios sin escribir el JOIN.
  • back_populates conecta los dos lados: si agregás un servicio a usuario.servicios, automáticamente servicio.profesional apunta a ese usuario. Quedan sincronizados.
  • cascade="all, delete-orphan": si borrás el usuario, se borran sus servicios; si sacás un servicio de la colección, queda "huérfano" y se elimina.
  • foreign_keys=...: hace falta porque servicios referencia a usuarios por varias FKs posibles; le aclaramos cuál usar para evitar ambigüedad.

Pregunta típica: «¿Diferencia entre ForeignKey y relationship?»

Respuesta: El ForeignKey es la restricción a nivel de base de datos (garantiza integridad referencial). El relationship existe sólo en el ORM: no crea ninguna columna, sino que te permite navegar los objetos relacionados en Python y que SQLAlchemy resuelva los JOINs / cargas por vos.

2. Configuración por entorno (12-factor)

La regla de oro: nada de secretos en el código. La configuración se lee de variables de entorno (o de un archivo .env en local) usando pydantic-settings.

backend/app/core/config.py (extracto)
class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

    DATABASE_URL: str = "postgresql+psycopg2://...localhost:5432/laburappdb"
    SECRET_KEY: str = "changeme"
    ACCESS_TOKEN_EXPIRE_MINUTES: int = 60 * 24

@lru_cache
def get_settings() -> Settings:
    return Settings()

settings = get_settings()
  • Cada campo se llena, en orden, desde una variable de entorno con ese nombre, o del .env, o el default. En producción inyectás DATABASE_URL y SECRET_KEY como env vars (en Fase 4/5, desde Secret Manager).
  • @lru_cache hace que Settings() se construya una sola vez (se cachea). Leer el entorno y parsearlo es algo que querés hacer al arrancar, no en cada request.
  • Pydantic convierte tipos: ACCESS_TOKEN_EXPIRE_MINUTES llega como string del entorno y se valida/castea a int.

12-factor app. Es una metodología para apps cloud. El factor III dice: «guardá la configuración en el entorno». Beneficio: la misma imagen Docker corre en local, staging y prod cambiando sólo variables — sin recompilar ni tocar código.

3. Engine, Session y get_db

Tres piezas que casi todo proyecto SQLAlchemy tiene:

backend/app/core/database.py
engine = create_engine(
    settings.DATABASE_URL,
    pool_pre_ping=True,   # revisa que la conexión siga viva antes de usarla
    echo=settings.ENVIRONMENT == "local",  # loguea el SQL en local
)
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)

class Base(DeclarativeBase):
    """Base declarativa para todos los modelos."""

def get_db() -> Generator:
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
  • Engine: el "motor" que administra el connection pool (un conjunto de conexiones reutilizables a la base). Crear conexiones es caro; el pool las recicla.
  • pool_pre_ping=True: antes de entregar una conexión, le hace un ping. Evita el clásico error de "conexión muerta" en entornos cloud (Cloud SQL puede cerrar conexiones ociosas).
  • Session: la "unidad de trabajo". Acumula cambios y los manda con commit(). SessionLocal() crea una sesión nueva.
  • get_db: un generador. Abre una sesión, la yield-ea al endpoint, y en el finally la cierra pase lo que pase. FastAPI lo usa como dependencia (ver sección 5).

Pregunta típica: «¿Por qué una sesión por request?»

Respuesta: Para aislar transacciones: cada request tiene su propia unidad de trabajo y su transacción. Si algo falla, se hace rollback de esa request sin afectar a otras. Y al cerrarla, la conexión vuelve al pool. Compartir una sesión global entre requests traería condiciones de carrera.

4. Seguridad: JWT + bcrypt

bcrypt — hashing de contraseñas

Hash ≠ cifrado. Un hash es de una sola vía: no se puede "desencriptar". Guardás el hash; cuando el usuario ingresa la contraseña, la volvés a hashear y comparás. bcrypt además es lento a propósito y usa salt (un valor aleatorio por contraseña), lo que frena los ataques de fuerza bruta y las rainbow tables.

backend/app/core/security.py (extracto)
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def hash_password(password: str) -> str:
    return pwd_context.hash(password)

def verify_password(plain: str, hashed: str) -> bool:
    return pwd_context.verify(plain, hashed)

JWT — tokens de sesión sin estado

¿Qué es un JWT? JSON Web Token: una cadena firmada con tres partes header.payload.signature. El servidor lo firma con SECRET_KEY; el cliente lo manda en cada request (Authorization: Bearer ...). El servidor verifica la firma y confía en el contenido sin guardar nada (stateless). Si la firma no valida, el token es falso o fue manipulado.

crear y decodificar el token
def create_access_token(subject: str, ...) -> str:
    expire = datetime.now(timezone.utc) + timedelta(minutes=...)
    payload = {"sub": subject, "exp": expire}  # sub = email; exp = expiración
    return jwt.encode(payload, settings.SECRET_KEY, algorithm=settings.ALGORITHM)

def decode_access_token(token: str) -> str | None:
    try:
        payload = jwt.decode(token, settings.SECRET_KEY, algorithms=[...])
        return payload.get("sub")  # devuelve el email si es válido
    except JWTError:
        return None
  • sub (subject): a quién pertenece el token. Acá usamos el email del usuario.
  • exp (expiration): cuándo deja de valer. jwt.decode rechaza solo los tokens vencidos.
  • Si alguien cambia un byte del token, la firma no coincide y jwt.decode lanza JWTError ⇒ devolvemos None.

Pregunta típica: «¿Sesiones en servidor o JWT?»

Respuesta: JWT es stateless: el servidor no guarda sesiones, escala horizontal sin sticky sessions ni store compartido. La contra: no se pueden "revocar" fácil antes de que expiren (por eso se usan expiraciones cortas y, si hace falta, refresh tokens o una blocklist).

5. Inyección de dependencias (DI)

FastAPI tiene un sistema de dependencias: funciones que se ejecutan antes del endpoint y le "inyectan" lo que necesita (la sesión de DB, el usuario actual, etc.). Se declaran con Depends().

backend/app/core/deps.py
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/api/v1/auth/login")
DbSession = Annotated[Session, Depends(get_db)]

def get_current_user(
    db: DbSession,
    token: Annotated[str, Depends(oauth2_scheme)],
) -> Usuario:
    email = decode_access_token(token)
    if email is None:
        raise HTTPException(401, "No se pudieron validar las credenciales")
    user = db.query(Usuario).filter(Usuario.email == email).first()
    if user is None:
        raise HTTPException(401, ...)
    return user

CurrentUser = Annotated[Usuario, Depends(get_current_user)]
  • DbSession y CurrentUser son alias de tipo. En un endpoint, declarar db: DbSession hace que FastAPI inyecte la sesión, y user: CurrentUser hace que valide el token y traiga el usuario.
  • OAuth2PasswordBearer le dice a FastAPI de dónde sacar el token (header Authorization: Bearer) y, de paso, hace que Swagger muestre el botón "Authorize".
  • Si no hay token válido, la dependencia corta con 401 antes de entrar al endpoint. El endpoint ya recibe un usuario seguro.

Por qué esto es elegante: proteger un endpoint es tan simple como agregar current_user: CurrentUser a su firma. La lógica de auth vive en un solo lugar y se reutiliza en toda la API.

6. App factory + lifespan

backend/app/main.py (extracto)
@asynccontextmanager
async def lifespan(app: FastAPI):
    # En local creamos las tablas al vuelo; en prod lo hace Alembic.
    if settings.ENVIRONMENT == "local":
        Base.metadata.create_all(bind=engine)
    yield

app = FastAPI(title=settings.PROJECT_NAME, lifespan=lifespan)
app.add_middleware(CORSMiddleware, allow_origins=settings.BACKEND_CORS_ORIGINS, ...)
app.include_router(api_router, prefix=settings.API_V1_PREFIX)
  • lifespan: código que corre al arrancar (antes del yield) y al apagar (después). Acá, en local, crea las tablas con create_all.
  • local vs prod: create_all es cómodo para iterar, pero no versiona cambios. En prod el esquema lo maneja Alembic (Fase 2) — más control, migraciones reversibles.
  • CORS: middleware que autoriza al frontend (localhost:5173) a llamar a la API desde el navegador.
  • include_router(..., prefix="/api/v1"): todo cuelga de /api/v1, versionando la API desde el día uno.

7. Docker base

El backend se empaqueta en una imagen para correr igual en cualquier lado.

backend/Dockerfile (idea original de Fase 1)
FROM python:3.12-slim
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt   # capa cacheable: sólo cambia si cambian las deps
COPY . .
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8080"]
  • python:3.12-slim: imagen base chica (menos superficie de ataque, descarga más rápida).
  • Orden de capas: copiar requirements.txt e instalar antes de copiar el código aprovecha el cache de Docker: si sólo cambia el código, no reinstala dependencias.
  • PYTHONUNBUFFERED=1: que los logs salgan al instante (clave para ver logs en Cloud Run / k8s).

En la Fase 4 este Dockerfile evoluciona: usuario no-root, y un entrypoint.sh que corre las migraciones antes de levantar el servidor. Lo vemos ahí.

Repaso de entrevista

«¿Qué ganás usando un ORM en vez de SQL crudo?»
Seguridad (parametrización ⇒ sin inyección SQL), productividad (objetos en vez de tuplas), portabilidad entre motores, y migraciones versionadas.

«¿Cómo evitás filtrar secretos?»
Config por entorno con pydantic-settings; en prod los valores vienen de Secret Manager. El repo sólo tiene .env.example con placeholders.

«¿Qué pasa en cada request, de punta a punta?»
FastAPI resuelve dependencias (get_db abre sesión, opcionalmente get_current_user valida el JWT) → corre el endpoint → la sesión hace commit/rollback → get_db la cierra y vuelve al pool.
