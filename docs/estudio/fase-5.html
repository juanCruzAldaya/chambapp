Fase 5 — Kubernetes / GKE

Lo mismo que hicimos en Cloud Run, pero orquestado con Kubernetes. Enfoque práctico: para estudiarlo, usarlo y defenderlo en una entrevista.

Kubernetes (k8s) es un orquestador de contenedores: vos le describís el estado deseado ("quiero 2 réplicas de esta imagen, expuestas acá, que se autoescalen") y él se encarga de lograrlo y mantenerlo — reinicia lo que se cae, reemplaza nodos, balancea carga. GKE es Kubernetes gestionado por Google (vos no administrás el "cerebro" del cluster).

La idea central: estado declarativo. No le decís a k8s "arrancá un contenedor" (imperativo). Le decís "el mundo debería verse así" (declarativo, en YAML) y un bucle de control (reconciliation loop) trabaja sin parar para que la realidad coincida con tu declaración. Si un pod muere, k8s nota la diferencia y crea otro. Esto es lo que hay que entender de verdad.

¿Cuándo usarlo? (y cuándo no)

Lo más valioso para una entrevista no es recitar objetos, es saber cuándo conviene. Sé honesto:

Usá Cloud Run / serverless si…Usá Kubernetes si…
Tenés pocos servicios y querés simpleza. Tenés muchos microservicios que coordinar.
El tráfico es variable y querés escalar a cero. Necesitás control fino: sidecars, jobs, demonios, redes internas, afinidad de nodos.
No querés gestionar infraestructura. Ya tenés un equipo de plataforma / requisitos multi-cloud o on-prem.
Es un MVP, un portfolio, una API chica. Cargas de trabajo complejas, stateful, o políticas de despliegue avanzadas.

Para chambapp, Cloud Run alcanza y sobra. La Fase 5 es de estudio: el objetivo es entender k8s con un proyecto real, no porque la app lo necesite. Decir esto en una entrevista demuestra criterio, no ignorancia: "elegí la herramienta más simple que resuelve el problema; sé usar k8s para cuando haga falta".

«¿Cuándo NO usarías Kubernetes?»
Cuando la complejidad operativa supera el beneficio: proyectos chicos, equipos sin plataforma, o cuando un serverless (Cloud Run/Lambda) cubre el caso. k8s es potente pero tiene un costo de operación y aprendizaje que hay que justificar.

El vocabulario mínimo

Con estos 8 objetos entendés el 90% de un cluster:

ObjetoQué es (en una línea)
PodLa unidad mínima: uno o más contenedores que comparten red y viven juntos. Efímero.
DeploymentMantiene N réplicas de un pod y maneja los rollouts (actualizaciones sin downtime) y rollbacks.
ServiceUna IP/nombre interno estable que balancea entre los pods (que van y vienen).
IngressEnrutador HTTP de entrada: mapea URLs/paths a Services. Es el Load Balancer público.
HPAHorizontalPodAutoscaler: ajusta el número de réplicas según CPU/memoria/métricas.
NamespaceUna "carpeta" lógica para aislar y agrupar recursos (ej. chambapp).
Secret / ConfigMapInyectan secretos / configuración a los pods como env vars o archivos.
JobCorre una tarea hasta completarse (ej. migraciones) y termina; no es un servicio.

La jerarquía mental. Un Deployment crea ReplicaSets que crean Pods que contienen contenedores. Un Service les da una dirección estable. Un Ingress abre la puerta desde internet a los Services.

Decisión de diseño: en k8s usamos el Ingress para servir front y API en el mismo dominio (/api/* → backend, el resto → frontend). Eso elimina el CORS: por eso la imagen del front se construye con VITE_API_URL=/api/v1 (relativo). Misma imagen base, distinta config de build.

El código, manifest por manifest

Todo vive en infra/k8s/. Los ${VAR} se resuelven con envsubst dentro de deploy.sh.

Deployment + sidecar del proxy

infra/k8s/04-backend.yaml (extracto)
kind: Deployment
spec:
  replicas: 2                      # estado deseado: 2 pods siempre
  template:
    spec:
      serviceAccountName: chambapp # identidad (Workload Identity)
      containers:
        - name: api
          image: ${API_IMAGE}
          env:
            - name: RUN_MIGRATIONS
              value: "false"     # las migra el Job, no cada réplica
          envFrom:
            - secretRef:
                name: chambapp-secrets   # DATABASE_URL, SECRET_KEY
          readinessProbe:
            httpGet: { path: /health, port: 8080 }  # ¿lista para recibir tráfico?
          livenessProbe:
            httpGet: { path: /health, port: 8080 }  # ¿hay que reiniciarla?
        - name: cloud-sql-proxy       # SIDECAR: 2º contenedor en el mismo pod
          image: gcr.io/cloud-sql-connectors/cloud-sql-proxy:2.14.1
          args: ["--port=5432", "${INSTANCE_CONNECTION_NAME}"]
  • replicas: 2: el Deployment garantiza dos pods. Si uno muere, crea otro. Para actualizar, hace rolling update (levanta los nuevos antes de bajar los viejos ⇒ sin downtime).
  • Sidecar: el pod tiene 2 contenedores — la API y el Cloud SQL Auth Proxy. Comparten localhost, así la app se conecta a 127.0.0.1:5432 y el proxy tuneliza a Cloud SQL. Es el patrón sidecar: un ayudante que vive pegado a la app.
  • readinessProbe: hasta que /health no responde OK, k8s no le manda tráfico (ni la cuenta como lista en un rollout).
  • livenessProbe: si deja de responder, k8s reinicia el contenedor. Autocuración.

Pod = contenedores que viven juntos. El sidecar muestra por qué el Pod (no el contenedor) es la unidad mínima: a veces necesitás procesos que compartan red y ciclo de vida (app + proxy, app + agente de logs, etc.).

Service

infra/k8s/04-backend.yaml (Service)
kind: Service
spec:
  type: ClusterIP            # IP interna (no expuesta a internet)
  selector:
    app: chambapp-api        # enruta a los pods con esta etiqueta
  ports:
    - port: 80
      targetPort: 8080       # el puerto del contenedor

¿Por qué hace falta un Service? Los pods son efímeros: nacen y mueren con IPs distintas. El Service te da un nombre e IP estables (chambapp-api) y balancea entre los pods vivos que matcheen el selector. Otros componentes hablan con el Service, no con pods directos.

Ingress

infra/k8s/07-ingress.yaml (extracto)
kind: Ingress
spec:
  rules:
    - http:
        paths:
          - path: /api/*           # todo lo que empiece con /api…
            backend: { service: { name: chambapp-api, port: { number: 80 } } }
          - path: /*               # …el resto
            backend: { service: { name: chambapp-web, port: { number: 80 } } }
  • Un solo Load Balancer para toda la app, con routing por path. En GKE, crear este Ingress provisiona un balanceador HTTP de Google.
  • Mismo origen ⇒ sin CORS: front y API comparten dominio.
  • El health check del balanceador usa las readinessProbe de los pods.

HPA — autoescalado

infra/k8s/08-hpa.yaml (extracto)
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef: { kind: Deployment, name: chambapp-api }
  minReplicas: 2
  maxReplicas: 6
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }

Traducción: "mantené el uso de CPU promedio cerca del 70%; si sube, agregá pods (hasta 6); si baja, sacá pods (mínimo 2)". k8s ajusta solo.

Secret + Workload Identity

infra/k8s/02-serviceaccount.yaml
kind: ServiceAccount
metadata:
  name: chambapp
  annotations:
    iam.gke.io/gcp-service-account: ${GSA_EMAIL}   # vincula KSA ↔ GSA de Google

Workload Identity. En vez de meter una clave JSON de Google en el pod (peligroso), se vincula la ServiceAccount de Kubernetes (KSA) con una ServiceAccount de Google (GSA) que tiene permiso de Cloud SQL. El proxy usa esa identidad automáticamente. Cero claves en el cluster. Es el mismo principio de WIF que vimos para CI/CD en la Fase 4.

El Secret con DATABASE_URL y SECRET_KEY lo crea deploy.sh con kubectl create secret (leyendo de Secret Manager), y el Deployment lo monta con envFrom.

Job de migración

infra/k8s/06-migrate-job.yaml (extracto)
kind: Job
spec:
  template:
    spec:
      restartPolicy: Never
      initContainers:
        - name: cloud-sql-proxy
          restartPolicy: Always      # ← "native sidecar": vive durante el job y se cierra solo
          image: ...cloud-sql-proxy:2.14.1
      containers:
        - name: migrate
          image: ${API_IMAGE}
          command: ["sh", "-c", "alembic upgrade head && python -m app.db.seed"]
  • ¿Por qué un Job y no el entrypoint? Con 2+ réplicas, si cada pod corriera las migraciones al arrancar, competirían entre sí. El Job las corre una sola vez, antes de actualizar los Deployments.
  • Native sidecar en un Job: el proxy va como initContainer con restartPolicy: Always. Así arranca primero, acompaña a la migración y k8s lo termina cuando el contenedor migrate finaliza (si fuera un container normal, el Job nunca "terminaría" porque el proxy no se apaga solo).

Empezar HOY — gratis y local

No necesitás GCP para aprender k8s. GKE cuesta plata, pero podés correr un cluster real en tu máquina, gratis, con kind (Kubernetes-in-Docker) o minikube. Los mismos manifests, los mismos kubectl. Es la mejor forma de practicar para una entrevista.

cluster local con kind (necesita Docker)
kind create cluster --name chambapp      # crea un cluster local en segundos
kubectl apply -f infra/k8s/01-namespace.yaml
kubectl get nodes                        # tu "cluster" de 1 nodo

Para practicar con chambapp localmente sin Cloud SQL, podrías agregar un Deployment de Postgres en el cluster y apuntar DATABASE_URL ahí (en vez del proxy). El resto (Deployments, Service, HPA, Job) funciona igual.

Diferencia local vs GKE: el Ingress tipo GCE y el Cloud SQL Auth Proxy son específicos de GCP. En local se usa el Ingress de nginx y un Postgres en el cluster. La lógica de los manifests es la misma — eso es lo que se estudia.

kubectl de bolsillo

kubectl es el comando para hablar con un cluster. Los que más vas a usar:

comandos esenciales
kubectl apply -f archivo.yaml          # crear/actualizar recursos (declarativo)
kubectl -n chambapp get pods           # listar pods del namespace
kubectl -n chambapp get deploy,svc,ingress,hpa   # panorama general
kubectl -n chambapp logs deploy/chambapp-api -c api   # ver logs de un contenedor
kubectl -n chambapp describe pod <pod> # diagnóstico detallado (eventos, estados)
kubectl -n chambapp rollout restart deploy/chambapp-api  # redeploy
kubectl -n chambapp scale deploy/chambapp-web --replicas=3  # escalar a mano
kubectl -n chambapp exec -it <pod> -- sh   # entrar a un contenedor

El flujo mental al debuggear: get pods (¿están corriendo?) → si uno está CrashLoopBackOff o Pending, describe pod (¿qué evento falló?) → logs (¿qué dice la app?). Ese trío resuelve la mayoría de los problemas.

Repaso de entrevista

«Explicame Pod vs Deployment vs Service.»
El Pod es la unidad que corre tus contenedores (efímera). El Deployment mantiene N réplicas de ese pod y gestiona actualizaciones sin downtime. El Service les da una IP/nombre estable y balancea tráfico entre los pods vivos.

«¿Qué es declarativo en Kubernetes?»
Describís el estado deseado en YAML y un control loop reconcilia la realidad con esa descripción continuamente. No ordenás acciones; declarás el resultado.

«¿Cómo conectás los pods a una base gestionada sin claves?»
Cloud SQL Auth Proxy como sidecar + Workload Identity: la ServiceAccount de k8s se vincula a una de Google con permiso de Cloud SQL; el proxy usa esa identidad. Cero credenciales en el cluster.

«¿Liveness vs readiness probe?»
Readiness: ¿el pod está listo para recibir tráfico? (si no, lo sacan del balanceo). Liveness: ¿el pod está sano? (si no, lo reinician). Distintos propósitos, ambos HTTP a /health en este proyecto.

«¿Por qué migraciones en un Job y no en el contenedor?»
Para que corran una sola vez y no en paralelo entre réplicas, evitando condiciones de carrera sobre el esquema. El Job termina; el Deployment sólo sirve tráfico.
