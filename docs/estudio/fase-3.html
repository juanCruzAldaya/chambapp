Fase 3 — Frontend con React

Una SPA en React 19 + TypeScript + Vite + Tailwind que consume la API de la Fase 2.

El frontend es una SPA (Single Page Application): el navegador carga una vez el HTML/JS y, a partir de ahí, React dibuja las vistas y pide datos a la API por fetch. Cubrimos: componentes y hooks, un cliente HTTP tipado, autenticación con Context, ruteo con rutas protegidas, y estilos con Tailwind.

SPA vs multipágina. En una web tradicional, cada click pide una página nueva al servidor. En una SPA, el ruteo ocurre en el navegador (react-router) y sólo se piden datos (JSON) a la API. Resultado: navegación instantánea y una separación limpia front/back.

1. React: componentes y JSX

Componente. Una función que recibe props y devuelve JSX (HTML con superpoderes). React llama a esa función y, cuando el estado cambia, la vuelve a llamar y actualiza sólo lo que cambió en el DOM. Es declarativo: vos describís cómo se ve la UI para un estado dado, no manipulás el DOM a mano.

frontend/src/components/ServiceCard.tsx (extracto)
export function ServiceCard({ servicio }: { servicio: Servicio }) {
  return (
    <Link to={`/servicios/${servicio.id}`}>
      <Card>
        <p>{servicio.description || "Sin descripción"}</p>
        <span>{formatRating(servicio.profesional?.calificacion_promedio)}</span>
      </Card>
    </Link>
  );
}
  • Props: { servicio } es la entrada del componente, tipada con TypeScript (servicio: Servicio).
  • { } en JSX: incrusta expresiones JavaScript. {servicio.description || "..."} muestra la descripción o un fallback.
  • Composición: ServiceCard usa Card y Link. La UI se arma combinando componentes chicos y reutilizables.
  • ?. (optional chaining): si profesional es null, no rompe; devuelve undefined.

2. Hooks

Los hooks son funciones que le dan "memoria" y efectos a los componentes. Los cuatro que más usa el proyecto:

HookPara qué
useStateGuardar estado local que, al cambiar, re-renderiza la UI.
useEffectEjecutar "efectos" (pedir datos, suscribirse) después de renderizar.
useCallbackMemorizar una función para que no se recree en cada render.
useMemoMemorizar un cálculo costoso/derivado.
patrón "cargar datos al montar"
const [servicios, setServicios] = useState<Servicio[]>([]);  # estado
const [loading, setLoading] = useState(true);

useEffect(() => {                       # efecto: corre después del 1er render
  api.searchServicios({})
    .then(setServicios)
    .finally(() => setLoading(false));
}, []);                                  # [] = "una sola vez al montar"
  • useState devuelve [valor, setter]. Llamar al setter dispara un re-render con el nuevo valor.
  • Array de dependencias de useEffect: [] ⇒ corre una vez (al montar). Si ponés variables, vuelve a correr cuando esas cambian. Es el origen de muchos bugs si se arma mal.
  • Estado de carga: el patrón loading permite mostrar un spinner mientras llega la respuesta.

Trampa clásica de useEffect: si una función se usa adentro y se define en cada render, ponerla en las dependencias causa un loop. Por eso envolvemos esas funciones en useCallback (memorizadas), como en el detalle de servicio del proyecto.

3. TypeScript de punta a punta

Los tipos del frontend reflejan los schemas Pydantic del backend. Así el editor te avisa si usás mal un campo.

frontend/src/lib/types.ts (extracto)
export interface Servicio {
  id: number;
  description: string | null;
  main_category: number;
  created_at: string;
  profesional: ProfesionalResumen | null;
  // Decimal del backend llega como string en JSON
}

Detalle real del proyecto: calificacion_promedio se tipa como string | null, no number. Pydantic serializa Decimal como string en JSON (ej. "4.50"). Lo descubrimos haciendo un smoke test con curl antes de codear el front. Tipar distinto te ahorra bugs sutiles.

4. Cliente fetch tipado

En vez de esparcir fetch por todos lados, hay una capa (lib/api.ts) que centraliza: URL base, el token JWT, los headers, el parseo de errores y el manejo del 401.

frontend/src/lib/api.ts (extracto)
async function request<T>(path: string, options = {}): Promise<T> {
  const headers: Record<string, string> = {};
  const token = getToken();
  if (token) headers["Authorization"] = `Bearer ${token}`;  # agrega el JWT
  ...
  const res = await fetch(url, { method, headers, body });
  if (res.status === 401) {                 # token vencido/ inválido
    clearToken();
    window.dispatchEvent(new Event("auth:logout"));  # avisa al Context
  }
  if (!res.ok) throw new ApiError(res.status, parseDetail(data));
  return data as T;
}
  • Genérico <T>: cada llamada declara qué tipo devuelve (request<Servicio[]>(...)), y TypeScript propaga ese tipo.
  • Token automático: si hay JWT guardado en localStorage, se agrega el header Authorization solo.
  • 401 centralizado: si el token venció, limpia el storage y emite un evento auth:logout que el Context escucha para deslogear.
  • ApiError: errores con status y mensaje legible (parseado del formato de error de FastAPI). Las páginas los muestran.

«¿Dónde guardás el JWT en el front?»
En este proyecto, localStorage (simple, persiste entre recargas). El trade-off: es accesible por JS, así que es vulnerable a XSS. La alternativa más segura es una cookie httpOnly, a costa de manejar CSRF. Para un portfolio, localStorage es razonable y hay que saber explicar el trade-off.

5. Context de autenticación

¿Qué es Context? Una forma de compartir estado "global" (acá: el usuario logueado) sin pasarlo por props por toda la jerarquía (prop drilling). Un Provider envuelve la app y cualquier componente lee el valor con un hook.

frontend/src/context/AuthContext.tsx (extracto)
const login = useCallback(async (email, password) => {
  const { access_token } = await api.login(email, password);
  setToken(access_token);              # guarda el JWT
  setUser(await api.me());           # trae el perfil
}, []);

useEffect(() => {                       # al cargar la app: si hay token, hidrata el usuario
  refresh().finally(() => setLoading(false));
  window.addEventListener("auth:logout", () => setUser(null));
}, [refresh]);
  • Hidratación: al abrir la app, si hay token guardado, pide /usuarios/me para recuperar el usuario. Así seguís logueado tras recargar.
  • Reacciona al 401: escucha el evento auth:logout que emite el cliente API y limpia el usuario. Logout automático cuando el token muere.
  • useAuth(): un hook (useContext) que cualquier componente usa para leer user, login, logout.

6. Router y rutas protegidas

frontend/src/App.tsx (extracto)
<Routes>
  <Route element={<Layout />}>
    {/* públicas */}
    <Route path="/" element={<HomePage />} />
    <Route path="/servicios/:id" element={<ServiceDetailPage />} />
    {/* protegidas */}
    <Route element={<ProtectedRoute />}>
      <Route path="/agenda" element={<AgendaPage />} />
      <Route path="/contrataciones" element={<ContractsPage />} />
    </Route>
  </Route>
</Routes>
frontend/src/components/ProtectedRoute.tsx
export function ProtectedRoute() {
  const { user, loading } = useAuth();
  if (loading) return <Spinner />;
  if (!user) return <Navigate to="/login" replace />;  # redirige si no hay sesión
  return <Outlet />;                              # renderiza la ruta hija
}
  • Rutas anidadas: Layout (navbar + footer) envuelve todo vía <Outlet/>; las páginas se renderizan adentro.
  • :id: parámetro de URL; la página lo lee con useParams().
  • Guardia: ProtectedRoute verifica la sesión. Sin usuario ⇒ redirige a /login. Las rutas hijas no se renderizan jamás sin auth.

La guardia del front es UX, no seguridad. Evita mostrar pantallas sin sentido, pero la seguridad real está en el backend (cada endpoint valida el JWT). Nunca confíes sólo en el front para proteger datos.

7. Una página real: detalle + contratar

La página de detalle del servicio junta todo: carga el servicio, sus reseñas y la disponibilidad del profesional en paralelo, y arma el formulario para contratar un turno.

frontend/src/pages/ServiceDetailPage.tsx (extracto)
const serv = await api.getServicio(servicioId);
const [revs, cals] = await Promise.all([      # 2 requests en paralelo
  api.listResenas(servicioId),
  api.getCalendariosDeUsuario(serv.profesional_id),
]);

const slots = useMemo(() =>                    # turnos disponibles, derivados
  disponibilidad.flatMap(cal =>
    cal.eventos.filter(e => e.estado === "disponible")
      .map(e => ({ ...e, calendario_id: cal.id }))),
  [disponibilidad]);
  • Promise.all: lanza dos llamadas a la vez y espera ambas. Más rápido que encadenarlas.
  • useMemo: la lista de turnos se deriva de la disponibilidad; se recalcula sólo si cambia, no en cada render.
  • Si el usuario es el dueño, no ve "contratar" sino una nota; si no está logueado, ve un CTA para ingresar. La UI reacciona al estado de auth.

8. Tailwind v4

Utility-first CSS. En vez de escribir CSS aparte, componés estilos con clases chiquitas directo en el JSX: className="flex items-center gap-2 rounded-lg". Ventaja: no inventás nombres de clases, no hay CSS muerto, y el diseño vive junto al markup.

Tailwind v4: setup mínimo
// vite.config.ts — plugin oficial, sin archivo de config
plugins: [react(), tailwindcss()]

/* index.css — una línea */
@import "tailwindcss";
  • v4 simplificó todo: se activa con el plugin de Vite y un @import. Sin tailwind.config.js obligatorio.
  • Tema: definimos colores de marca con @theme y los usamos como bg-marca-600.
  • Build: Tailwind escanea el código y genera sólo las clases usadas ⇒ CSS final chico (~20 KB en este proyecto).

Repaso de entrevista

«¿Qué es el array de dependencias de useEffect?»
La lista de valores que, al cambiar, hacen que el efecto vuelva a correr. [] = sólo al montar. Omitirlo = en cada render. Mal armado, causa loops o datos viejos (stale closures).

«¿Cómo manejás la sesión en una SPA?»
JWT en localStorage + un Context que hidrata el usuario al cargar y escucha 401 para deslogear. Las rutas privadas usan una guardia, pero la autorización real la impone el backend.

«¿Por qué un cliente API centralizado?»
Para no repetir lógica de headers/errores/auth, tener tipos en un solo lugar y poder cambiar el manejo de 401 o la URL base sin tocar cada componente.
