Producción — el circuito real

Cómo pusimos chambapp en vivo y accesible, de punta a punta: arquitectura, comandos reales, los bugs que aparecieron y cómo se resolvieron.

Esta página documenta el despliegue real (no teórico) que dejó la app online y gratis: frontend en Firebase Hosting, backend en Cloud Run y base en Supabase. Incluye los cuatro problemas que aparecieron en el camino y cómo se diagnosticaron — que es lo más útil para aprender de verdad y para una entrevista.

Ojo: difiere de la Fase 4 "de manual". La guía de la Fase 4 describe el patrón clásico (frontend y backend en Cloud Run + Cloud SQL). Acá optamos por una variante $0 real: Firebase Hosting para el front y Supabase para la DB, porque Cloud SQL no tiene free tier. Saber elegir la variante barata también es ingeniería.

1. La arquitectura elegida

Navegador │ ▼ https://chambapp-a0472.web.app ┌─────────────────────────┐ │ Firebase Hosting │ sirve la SPA (HTML/JS/CSS) por CDN │ (rewrites) │ └───────────┬─────────────┘ │ /api/** → reescritura a Cloud Run (MISMO dominio) ▼ ┌─────────────────────────┐ │ Cloud Run │ FastAPI (escala a cero) │ chambapp-api │ └───────────┬─────────────┘ │ Session pooler (IPv4) + SSL ▼ ┌─────────────────────────┐ │ Supabase (Postgres) │ datos └─────────────────────────┘

La clave del diseño: todo bajo el mismo dominio. Firebase Hosting sirve la SPA y, cuando el navegador pide /api/**, lo reescribe hacia el servicio de Cloud Run. Para el browser, front y API viven en chambapp-a0472.web.app ⇒ no hay CORS.

firebase.json — el corazón de la integración
{
  "hosting": {
    "public": "frontend/dist",
    "rewrites": [
      { "source": "/api/**",
        "run": { "serviceId": "chambapp-api", "region": "us-central1" } },
      { "source": "**", "destination": "/index.html" }
    ]
  }
}
  • Primera regla: /api/** va a Cloud Run (Firebase preserva el path completo, así /api/v1/auth/login llega igual al backend).
  • Segunda regla: cualquier otra ruta cae en index.html (fallback de la SPA, para que react-router maneje el ruteo en el cliente).
  • Consecuencia: el front se buildea con VITE_API_URL=/api/v1 (relativo). Cero configuración de CORS, cero URLs cruzadas.

2. Decisiones (y por qué)

DecisiónPor qué
Frontend en Firebase Hosting (no Cloud Run) Es estático: CDN global gratis, deploy de un comando, y el rewrite a Cloud Run elimina el CORS. Más simple que servir nginx en otro Cloud Run.
DB en Supabase (no Cloud SQL) Cloud SQL no tiene free tier (~USD 8-10/mes). Supabase da Postgres gratis. El objetivo era $0.
Session pooler de Supabase (no conexión directa) La conexión directa de Supabase es IPv6; Cloud Run hace egress IPv4. El Session pooler (Supavisor) es IPv4 y se comporta como un Postgres normal (a diferencia del Transaction pooler, que rompe con SQLAlchemy).
Secretos en Secret Manager La DATABASE_URL lleva la contraseña del pooler; nunca en el repo ni en variables de entorno planas.
Migraciones en el entrypoint Al arrancar, alembic upgrade head crea/actualiza el esquema en Supabase antes de servir.

«¿Por qué no Cloud SQL?»
Porque el requisito era costo cero y Cloud SQL no tiene free tier. Supabase ofrece Postgres gratis y, usando el Session pooler (IPv4), se integra sin problema con Cloud Run. Es una decisión de costo/beneficio, no técnica: Cloud SQL sería la opción si hubiera presupuesto y se quisiera todo dentro de GCP.

3. La base: Supabase

Pasos en el dashboard de Supabase:

  1. Crear proyecto (nombre, password de DB, región — elegimos us-east-1).
  2. Desmarcar "Enable Data API" (no usamos la API REST automática de Supabase; entramos directo al Postgres desde nuestra FastAPI).
  3. Connect → Session pooler para obtener el connection string IPv4.
forma del connection string (Session pooler)
postgresql://postgres.<ref>:<password>@aws-1-us-east-1.pooler.supabase.com:5432/postgres
       └ usuario con el ref ┘                └ host del pooler (IPv4) ┘

Para nuestra app lo transformamos al formato de SQLAlchemy + psycopg2, agregando SSL:

DATABASE_URL final (va a Secret Manager)
postgresql+psycopg2://postgres.<ref>:<password>@aws-1-us-east-1.pooler.supabase.com:5432/postgres?sslmode=require

Detalle del usuario del pooler. El usuario es postgres.<ref> (con el ref del proyecto). Supavisor usa ese prefijo para saber a qué proyecto enrutar, y del lado del servidor autentica como postgres. Por eso un error "auth failed for user postgres" no significa que el usuario esté mal escrito.

4. Backend a Cloud Run

El recorrido completo, con los comandos reales (sin Docker local: build con Cloud Build):

4.1 — Proyecto, APIs y repo de imágenes
gcloud config set project chambapp-a0472
gcloud services enable run.googleapis.com cloudbuild.googleapis.com \
  artifactregistry.googleapis.com secretmanager.googleapis.com
gcloud artifacts repositories create chambapp \
  --repository-format=docker --location=us-central1
4.2 — Secretos en Secret Manager
printf '%s' 'postgresql+psycopg2://...pooler.supabase.com:5432/postgres?sslmode=require' \
  | gcloud secrets create DATABASE_URL --data-file=-
openssl rand -hex 32 | gcloud secrets create SECRET_KEY --data-file=-

# permiso de lectura a la service account de runtime de Cloud Run:
gcloud projects add-iam-policy-binding chambapp-a0472 \
  --member="serviceAccount:<PROJECT_NUMBER>-compute@developer.gserviceaccount.com" \
  --role=roles/secretmanager.secretAccessor
4.3 — Build de la imagen (Cloud Build) y deploy
gcloud builds submit backend \
  --tag us-central1-docker.pkg.dev/chambapp-a0472/chambapp/chambapp-api:TAG

gcloud run deploy chambapp-api \
  --image=us-central1-docker.pkg.dev/chambapp-a0472/chambapp/chambapp-api:TAG \
  --region=us-central1 --allow-unauthenticated \
  --set-env-vars="^##^ENVIRONMENT=production##SEED_ON_START=false##BACKEND_CORS_ORIGINS=https://chambapp-a0472.web.app,https://chambapp-a0472.firebaseapp.com" \
  --set-secrets=DATABASE_URL=DATABASE_URL:latest,SECRET_KEY=SECRET_KEY:latest
  • gcloud builds submit: sube la carpeta backend/ y la buildea en la nube (no hace falta Docker local).
  • --allow-unauthenticated: el servicio es público (la autenticación la maneja la app con JWT, no Cloud Run).
  • --set-secrets: monta los secretos como variables de entorno en runtime. La imagen no contiene ningún secreto.
  • Al arrancar, el entrypoint corre alembic upgrade head y crea las tablas en Supabase.

Verificación rápida del backend:

curl https://chambapp-api-...run.app/health            # {"status":"healthy"}
curl https://chambapp-api-...run.app/api/v1/categorias # las 10 categorías

5. Frontend a Firebase Hosting

5.1 — Build + deploy
# el front se buildea con VITE_API_URL=/api/v1 (default) → mismo origen
cd frontend && npm run build && cd ..
firebase deploy --only hosting --project chambapp-a0472
  • Firebase sube el contenido de frontend/dist a su CDN.
  • Aplica las rewrites de firebase.json: la integración con Cloud Run queda activa al instante.
  • Requiere que el proyecto Firebase esté en plan Blaze (billing linkeado) — es lo que habilita el rewrite a Cloud Run. Igual sigue dentro del free tier.
5.2 — Verificación end-to-end (por el dominio del front)
curl https://chambapp-a0472.web.app/                    # 200, HTML de la SPA
curl https://chambapp-a0472.web.app/api/v1/categorias   # 10 → ¡el rewrite funciona!
curl -X POST https://chambapp-a0472.web.app/api/v1/auth/login \
  -d 'username=...&password=...'                         # devuelve un JWT

Que /api/v1/categorias responda desde el dominio de Firebase prueba que el rewrite a Cloud Run está enrutando bien y que es todo mismo origen.

6. Los problemas reales (y cómo se resolvieron)

El deploy no salió de una. Aparecieron cuatro problemas — esta es la parte más formativa, porque muestra el método de diagnóstico.

Bug 1 — El contenedor crasheaba al arrancar (CORS / pydantic-settings)

Síntoma: Cloud Run fallaba con "container failed to start and listen on PORT". Diagnóstico: leer los logs.

cómo se leyeron los logs del fallo
gcloud logging read \
  'resource.type="cloud_run_revision" AND resource.labels.service_name="chambapp-api"' \
  --limit=40 --freshness=10m --format='value(textPayload)'

El traceback mostraba que pydantic-settings reventaba al construir Settings(). Causa: el campo BACKEND_CORS_ORIGINS es list[str]; cuando se pasa por una variable de entorno, pydantic-settings intenta parsearla como JSON, y nuestro valor (CSV: "a,b") no es JSON válido. Nunca se había notado porque en local/tests se usaba el default (una lista de Python).

el fix en app/core/config.py
from typing import Annotated
from pydantic_settings import BaseSettings, NoDecode, SettingsConfigDict

# NoDecode: que NO intente JSON; lo separa nuestro validador (mode="before")
BACKEND_CORS_ORIGINS: Annotated[list[str], NoDecode] = ["http://localhost:5173"]

Lección. Un bug latente sólo aparece cuando cambia el entorno (acá: setear la var por primera vez en prod). Por eso "funciona en mi máquina" no alcanza: hay que probar la config de producción.

Bug 2 — "password authentication failed for user postgres"

Síntoma: tras arreglar el bug 1, el contenedor seguía sin arrancar; los logs mostraban que alembic no podía conectar a Supabase: auth fallida. Causa: la contraseña que teníamos no era la real de la base. Fix: resetear la password en Supabase (Settings → Database → Reset database password) y actualizar el secreto con una nueva versión:

actualizar el secreto (nueva versión)
printf '%s' 'postgresql+psycopg2://postgres.<ref>:<NUEVA_PASS>@...pooler...:5432/postgres?sslmode=require' \
  | gcloud secrets versions add DATABASE_URL --data-file=-
# como el deploy usa DATABASE_URL:latest, el próximo arranque toma la nueva

Truco de diagnóstico. Para descartar que el problema fuera del lado de la app, probamos la conexión directo con psycopg2 desde la consola (con la password nueva). 5 de 5 conexiones OK ⇒ la credencial era correcta y el problema previo era la password vieja.

Bug 3 — La coma de gcloud

Síntoma: gcloud run deploy tiraba un error de parseo de flags. Causa: --set-env-vars usa la coma para separar pares clave=valor, pero nuestro BACKEND_CORS_ORIGINS contiene una coma (dos orígenes). Fix: el delimitador alternativo de gcloud, anteponiendo ^##^ para usar ## como separador:

delimitador alternativo
--set-env-vars="^##^ENVIRONMENT=production##BACKEND_CORS_ORIGINS=https://a.web.app,https://b.firebaseapp.com"
#               └ usa ## como separador, así la coma queda dentro del valor

Bug 4 — El seed falló (glitch transitorio del pooler)

Síntoma: las migraciones corrieron OK (¡tablas creadas!), pero el seed que corría justo después falló con auth — con la misma URL que recién había funcionado. Causa probable: propagación de la password recién reseteada entre nodos del pooler. Fix pragmático: en vez de depender del arranque, corrimos el seed una vez desde la consola (conexión confiable) contra la DB de prod, y desplegamos con SEED_ON_START=false.

seed manual contra prod, una sola vez
DATABASE_URL="postgresql+psycopg2://...pooler...:5432/postgres?sslmode=require" \
  ENVIRONMENT=production python -m app.db.seed
# → "Seed completo: 10 categorías y 44 subcategorías nuevas."

Lección. No todo se resuelve "en el sistema": a veces lo pragmático es sacar un paso frágil del camino crítico (el arranque) y hacerlo aparte. El seed es idempotente, así que correrlo a mano es seguro.

7. Una request en producción, paso a paso

Qué pasa cuando alguien hace login desde la app en vivo:

1. Browser → GET https://chambapp-a0472.web.app/ (Firebase CDN devuelve la SPA) 2. React arranca; el usuario completa el form de login 3. fetch POST /api/v1/auth/login (URL relativa, mismo origen) 4. Firebase Hosting matchea la rewrite /api/** → reenvía a Cloud Run (chambapp-api) 5. Cloud Run levanta una instancia si estaba en cero (cold start) y corre FastAPI 6. FastAPI valida credenciales: consulta Supabase por el Session pooler (IPv4 + SSL) 7. bcrypt verifica el hash; se firma un JWT con SECRET_KEY (de Secret Manager) 8. Respuesta { access_token } → vuelve por Firebase → al browser 9. El front guarda el JWT en localStorage; las próximas requests llevan Authorization: Bearer

Sin CORS en ningún punto. Como el browser siempre habla con chambapp-a0472.web.app (el salto a Cloud Run es server-side, transparente), nunca hay una petición cross-origin. Por eso no hubo que pelear con preflights.

8. Operar y redeploy

redeploy del backend
gcloud builds submit backend --tag .../chambapp-api:NUEVO_TAG
gcloud run deploy chambapp-api --image .../chambapp-api:NUEVO_TAG --region us-central1 \
  --allow-unauthenticated \
  --set-secrets=DATABASE_URL=DATABASE_URL:latest,SECRET_KEY=SECRET_KEY:latest
redeploy del frontend
cd frontend && npm run build && cd ..
firebase deploy --only hosting --project chambapp-a0472
observabilidad
gcloud run services describe chambapp-api --region us-central1   # estado, URL, revisión
gcloud logging read 'resource.labels.service_name="chambapp-api"' --limit=50 --freshness=1h
gcloud run revisions list --service chambapp-api --region us-central1

Hay un workflow de GitHub Actions (.github/workflows/deploy.yml) listo para automatizar esto en cada push a main vía Cloud Build + Workload Identity Federation. Se activa con la variable DEPLOY_ENABLED=true y los secrets de WIF (ver Fase 4).

9. Costos y gotchas

  • Costo ≈ $0: Firebase Hosting (free tier) + Cloud Run (escala a cero, free tier) + Supabase (free). Sólo Artifact Registry usa unos MB de storage (despreciable).
  • Plan Blaze: el proyecto tiene billing linkeado (lo exige el rewrite Firebase→Cloud Run). Conviene poner una alerta de presupuesto en GCP Billing por las dudas.
  • Supabase free pausa el proyecto tras ~7 días sin actividad: si un día la app no trae datos, entrá al dashboard de Supabase y lo reactivás.
  • Cold start: con escala a cero, la primera request tras inactividad tarda un poco más. Se puede fijar --min-instances=1 (a costa de pagar siempre una instancia).
  • Bajar todo si querés dejar de mantenerlo: gcloud run services delete chambapp-api --region us-central1, borrar el sitio de Firebase Hosting y pausar/borrar el proyecto de Supabase.

Repaso de entrevista

«Contame un deploy que se haya complicado.»
El contenedor no arrancaba en Cloud Run. Leí los logs con gcloud logging read y encontré que pydantic-settings intentaba parsear una env var de tipo lista como JSON; lo arreglé con NoDecode. Después apareció un error de auth a la DB (password desactualizada): lo verifiqué conectando con psycopg2 a mano, reseteé la password y actualicé el secreto. Método: reproducir, aislar, arreglar.

«¿Cómo evitaste el CORS entre front y back?»
Sirviendo ambos bajo el mismo dominio: Firebase Hosting reescribe /api/** al servicio de Cloud Run. El salto es server-side, así que el browser nunca hace una request cross-origin.

«¿Cómo conectaste Cloud Run con una DB externa gratis?»
Supabase por el Session pooler (Supavisor), que expone IPv4 — necesario porque Cloud Run hace egress IPv4 y la conexión directa de Supabase es IPv6. La URL va en Secret Manager con sslmode=require.
