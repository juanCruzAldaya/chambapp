Fase 4 — Docker & Cloud Run

Empaquetar en contenedores y desplegar serverless en GCP, con base gestionada, secretos y CI/CD.

Pasamos de "corre en mi máquina" a "corre en la nube". Empaquetamos backend y frontend en imágenes Docker, las publicamos en Artifact Registry y las desplegamos en Cloud Run (serverless), con la base en Cloud SQL, los secretos en Secret Manager y despliegues automáticos con CI/CD.

1. Docker

¿Qué es un contenedor? Un paquete que incluye tu app y todo lo que necesita (runtime, librerías, sistema base) para correr igual en cualquier máquina. A diferencia de una VM, no lleva un SO completo: comparte el kernel del host, así que es liviano y arranca en segundos. La imagen es la receta inmutable; el contenedor es una instancia corriendo.

Imagen del backend (con migraciones al arrancar)

backend/entrypoint.sh
#!/bin/sh
set -e
if [ "${RUN_MIGRATIONS:-true}" = "true" ]; then
  alembic upgrade head            # aplica migraciones antes de servir
fi
exec uvicorn app.main:app --host 0.0.0.0 --port "${PORT:-8080}"
  • entrypoint.sh: en prod, antes de levantar el servidor, corre alembic upgrade head. Así el esquema siempre está al día. (Se puede apagar con RUN_MIGRATIONS=false — útil cuando las migra un Job aparte, como en GKE.)
  • $PORT: Cloud Run inyecta el puerto por variable de entorno; el contenedor debe escuchar ahí. Por eso no hardcodeamos 8080.
  • Usuario no-root: el Dockerfile crea un usuario sin privilegios (appuser). Si alguien compromete el proceso, no es root. Buena práctica.

Imagen del frontend (build multi-stage)

frontend/Dockerfile (idea)
# Etapa 1: build con Node
FROM node:22-alpine AS build
COPY package*.json ./
RUN npm ci
COPY . .
ARG VITE_API_URL=/api/v1
RUN echo "VITE_API_URL=$VITE_API_URL" > .env.production && npm run build

# Etapa 2: servir estático con nginx (imagen final chiquita)
FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf.template /etc/nginx/templates/default.conf.template

Build multi-stage. La etapa 1 usa Node (pesado: ~400 MB con node_modules) sólo para compilar. La etapa 2 se queda únicamente con el resultado (dist/) servido por nginx. La imagen final no lleva Node ni node_modules ⇒ chica, rápida y con menos superficie de ataque.

  • VITE_API_URL se hornea en build: Vite reemplaza import.meta.env.VITE_API_URL por su valor al compilar. En Cloud Run apunta a la URL de la API; en GKE es /api/v1 (mismo origen).
  • nginx + $PORT: la imagen oficial sustituye ${PORT} en su config al arrancar (envsubst), así nginx escucha el puerto que Cloud Run le pide.

2. Cloud Run

¿Qué es Cloud Run? Un servicio serverless para contenedores: le das una imagen y Google la corre, la escala automáticamente (incluso a cero si no hay tráfico) y te cobra por uso. No gestionás servidores. Ideal para APIs y webs con tráfico variable.

deploy de la API (extracto de deploy-backend.sh)
gcloud run deploy chambapp-api \
  --image=$IMAGE \
  --region=$REGION \
  --allow-unauthenticated \
  --add-cloudsql-instances=$INSTANCE_CONNECTION_NAME \
  --set-env-vars=ENVIRONMENT=production \
  --set-secrets=DATABASE_URL=DATABASE_URL:latest,SECRET_KEY=SECRET_KEY:latest
  • Escala a cero: si nadie usa la app, no hay instancias y no pagás cómputo. Por eso Cloud Run es prácticamente gratis para un portfolio.
  • --set-secrets: inyecta secretos desde Secret Manager como variables de entorno. El secreto nunca está en la imagen ni en el repo.
  • --add-cloudsql-instances: monta la conexión segura a Cloud SQL (ver abajo).

Cold starts. El precio de escalar a cero: la primera request tras un rato "despierta" una instancia y tarda un poco más. Se mitiga con min-instances ≥ 1 (a costa de pagar siempre). Trade-off clásico de serverless.

3. Cloud SQL

Base gestionada. Cloud SQL es Postgres administrado por Google: backups, parches, alta disponibilidad y réplicas sin que vos administres el servidor. Vos te ocupás del esquema y los datos; la infraestructura la maneja GCP.

La conexión usa un unix socket seguro en vez de exponer la base a internet:

DATABASE_URL para Cloud Run + Cloud SQL
postgresql+psycopg2://USER:PASS@/chambappdb?host=/cloudsql/PROYECTO:REGION:INSTANCIA
  • Sin IP pública expuesta: Cloud Run habla con Cloud SQL por un socket interno (/cloudsql/...), no por una IP abierta a internet. Más seguro.
  • Mismo código, distinta URL: la app no cambia; sólo cambia DATABASE_URL (en local apunta a localhost, en prod al socket). Es el pago de haber hecho config 12-factor en la Fase 1.

4. Secret Manager

¿Por qué no env vars normales? Las variables de entorno comunes quedan visibles en la config del servicio y en logs. Secret Manager guarda los valores cifrados, versionados y con control de acceso (IAM). Sólo la service account autorizada los lee, en tiempo de ejecución.

crear secretos (setup.sh)
printf '%s' "$DATABASE_URL" | gcloud secrets create DATABASE_URL --data-file=-
gcloud secrets create SECRET_KEY --data-file=- <<< "$(openssl rand -hex 32)"
# y se le da acceso a la service account de Cloud Run:
gcloud projects add-iam-policy-binding $PROJECT \
  --member="serviceAccount:$RUNTIME_SA" --role=roles/secretmanager.secretAccessor

Esto cierra el círculo del aprendizaje de la Fase 1: el repo no tiene ni un secreto. Sólo .env.example con placeholders.

5. Artifact Registry

Registro de imágenes. Es el "GitHub de las imágenes Docker": donde se publican (push) las imágenes versionadas para que Cloud Run (o GKE) las descarguen. Cada imagen se etiqueta, típicamente con el hash del commit, para saber exactamente qué versión está corriendo.

ruta de una imagen
us-central1-docker.pkg.dev/PROYECTO/chambapp/chambapp-api:9e9c6e8
└── región ──────────────┘ └proyecto┘ └repo──┘ └servicio─┘ └tag (commit)┘

6. CI/CD

CI vs CD. CI (Integración Continua): en cada push/PR se corren tests y linters automáticamente, para detectar errores temprano. CD (Despliegue Continuo): si CI pasa, se construye y despliega solo. Menos errores humanos, despliegues repetibles.

CI — GitHub Actions (siempre activo)

.github/workflows/ci.yml (extracto)
jobs:
  backend:
    steps:
      - run: pip install -r requirements-dev.txt
      - run: ruff check app tests alembic    # lint
      - run: pytest                           # 30 tests
  frontend:
    steps:
      - run: npm ci
      - run: npm run build                    # typecheck + build

CD — Cloud Build + Workload Identity Federation

.github/workflows/deploy.yml (extracto)
- uses: google-github-actions/auth@v2
  with:
    workload_identity_provider: ${{ secrets.GCP_WORKLOAD_IDENTITY_PROVIDER }}
    service_account: ${{ secrets.GCP_DEPLOY_SA }}
- run: gcloud builds submit --config infra/cloudrun/cloudbuild.yaml ...

Workload Identity Federation (WIF). Permite que GitHub Actions se autentique en GCP sin una clave de service account (sin archivos JSON que se puedan filtrar). GitHub presenta un token OIDC que GCP confía según reglas (sólo este repo). Es la forma moderna y segura de hacer CD.

«¿Cómo evitás claves de service account en CI?»
Con Workload Identity Federation: el pipeline se autentica vía OIDC y "impersona" una service account con permisos acotados, sin guardar claves estáticas. Si se filtra el repo, no hay credencial que robar.

Repaso de entrevista

«¿Contenedor vs máquina virtual?»
La VM virtualiza hardware y lleva un SO completo; el contenedor comparte el kernel del host y sólo empaqueta la app y sus dependencias. Resultado: arranca en segundos, pesa poco y es portable.

«¿Por qué Cloud Run para este proyecto?»
Serverless, escala a cero (casi gratis con poco tráfico), despliegue de una imagen sin gestionar servidores. Perfecto para un portfolio o un MVP de tráfico variable.

«¿Cómo manejás migraciones en el deploy?»
El entrypoint corre alembic upgrade head antes de servir. En arquitecturas con muchas réplicas, se desacopla en un job/step separado para que no corran en paralelo.
