1. Schemas Pydantic v2

Modelo ORM ≠ Schema. El modelo (Fase 1) representa la tabla. El schema Pydantic define qué entra y qué sale por la API. Separarlos te da control: validás la entrada y, sobre todo, elegís qué exponer (nunca el password).

backend/app/schemas/user.py (extracto)
class UsuarioCreate(UsuarioBase):
    email: EmailStr                                # valida formato de email
    password: str = Field(min_length=8, max_length=128)

class UsuarioRead(UsuarioBase):
    model_config = ConfigDict(from_attributes=True)
    id: int
    email: EmailStr
    calificacion_promedio: Decimal | None = None
    created_at: datetime
    # OJO: no hay campo "password". Nunca sale al cliente.
  • UsuarioCreate (entrada): exige email válido y password de 8+ caracteres. Si no cumple, FastAPI responde 422 con el detalle, sin que escribas validación a mano.
  • UsuarioRead (salida): define exactamente los campos que el cliente ve. Como no incluye password, es imposible filtrarlo (el error clásico del proyecto original).
  • from_attributes=True: permite crear el schema directamente desde el objeto ORM (UsuarioRead.model_validate(usuario)), leyendo sus atributos. FastAPI lo hace solo al devolver el modelo.
  • EmailStr, Field(min_length=...): validadores declarativos. El tipo es la validación.

Validación de negocio en el schema: la reseña valida calificacion: int = Field(ge=1, le=5) (entre 1 y 5) y el evento valida con un model_validator que hora_fin > hora_inicio. La regla vive cerca del dato.

2. Routers y endpoints

Cada dominio es un APIRouter en app/api/routes/, y todos se montan en un router central con su prefijo y tag.

backend/app/api/router.py (extracto)
api_router = APIRouter()
api_router.include_router(auth.router, prefix="/auth", tags=["auth"])
api_router.include_router(users.router, prefix="/usuarios", tags=["usuarios"])
api_router.include_router(services.router, prefix="/servicios", tags=["servicios"])
# ... categorias, calendarios, eventos, contrataciones, resenas, etc.
  • Modularidad: un archivo por dominio. Fácil de navegar y testear.
  • tags: agrupan los endpoints en Swagger (/docs), que FastAPI genera automáticamente desde los tipos.
  • prefix: la ruta final es /api/v1 + /servicios + la ruta del endpoint.

3. Flujo de autenticación (de punta a punta)

backend/app/api/routes/auth.py (extracto)
@router.post("/register", response_model=UsuarioRead, status_code=201)
def register(payload: UsuarioCreate, db: DbSession) -> Usuario:
    if db.query(Usuario).filter(Usuario.email == payload.email).first():
        raise HTTPException(409, "Ya existe un usuario con ese email")
    usuario = Usuario(email=payload.email, password=hash_password(payload.password), ...)
    db.add(usuario); db.commit(); db.refresh(usuario)
    return usuario

@router.post("/login", response_model=Token)
def login(form_data: Annotated[OAuth2PasswordRequestForm, Depends()], db: DbSession):
    usuario = db.query(Usuario).filter(Usuario.email == form_data.username).first()
    if usuario is None or not verify_password(form_data.password, usuario.password):
        raise HTTPException(401, "Email o contraseña incorrectos")
    return Token(access_token=create_access_token(subject=usuario.email))

El recorrido completo:

  1. Registro: valida que el email no exista (si existe ⇒ 409 Conflict), hashea el password y guarda. Devuelve UsuarioRead (sin password) con 201 Created.
  2. Login: usa OAuth2PasswordRequestForm (el estándar: campos username y password en form-urlencoded). Busca el usuario, verifica el hash con bcrypt y, si todo bien, firma un JWT.
  3. Request protegida: el cliente manda Authorization: Bearer <token>; la dependencia get_current_user (Fase 1) lo valida y entrega el usuario.

Detalle de seguridad: ante credenciales malas, el mensaje es genérico ("email o contraseña incorrectos") — no revela si el email existe. Y la verificación usa verify_password aunque el usuario no exista, para no filtrar info por el tiempo de respuesta.

«¿Por qué el login usa form-urlencoded y no JSON?»
Porque seguimos el estándar OAuth2 password flow, que FastAPI implementa con OAuth2PasswordRequestForm. Eso hace que el botón "Authorize" de Swagger funcione directo y que clientes OAuth2 estándar interoperen.

4. Patrones de los endpoints

Búsqueda con filtros opcionales

backend/app/api/routes/services.py (extracto)
@router.get("", response_model=list[ServicioRead])
def search_servicios(db: DbSession, q: str | None = None,
                     main_category: int | None = None,
                     locality: str | None = None,
                     skip: int = 0, limit: int = 20):
    query = db.query(Servicio).options(joinedload(Servicio.profesional), ...)
    if q:             query = query.filter(Servicio.description.ilike(f"%{q}%"))
    if main_category: query = query.filter(Servicio.main_category == main_category)
    if locality:      query = query.filter(Servicio.locality == locality)
    return query.order_by(Servicio.created_at.desc()).offset(skip).limit(limit).all()
  • Query dinámica: arrancás de una query base y vas encadenando .filter() sólo por los parámetros presentes. Es el patrón estándar para búsquedas con filtros opcionales.
  • joinedload: trae el profesional y la categoría en el mismo query (evita el problema N+1: 1 consulta en vez de N).
  • offset/limit: paginación. ilike es búsqueda de texto case-insensitive.

Problema N+1. Si listás 20 servicios y por cada uno accedés a servicio.profesional sin precargar, son 1 + 20 = 21 queries. Con joinedload/selectinload lo resolvés en 1–2 queries. Es de las optimizaciones más preguntadas con ORMs.

Permisos: sólo el dueño modifica

PATCH /servicios/{id} (extracto)
servicio = _get_servicio_o_404(db, servicio_id)
if servicio.profesional_id != current_user.id:
    raise HTTPException(403, "No podés modificar un servicio que no es tuyo")

for campo, valor in datos.items():
    setattr(servicio, campo, valor)
db.commit()
  • 404 vs 403: si no existe ⇒ 404; si existe pero no es tuyo ⇒ 403 Forbidden. Distinción importante en una API REST.
  • exclude_unset=True: hace el PATCH parcial real — sólo toca los campos que el cliente envió, no pisa el resto con None.

Efecto secundario: recalcular el promedio

backend/app/api/routes/reviews.py (extracto)
def _recalcular_promedio_profesional(db, profesional_id):
    promedio = (db.query(func.avg(Resena.calificacion))
                  .join(Servicio, Resena.servicio_id == Servicio.id)
                  .filter(Servicio.profesional_id == profesional_id).scalar())
    profesional = db.get(Usuario, profesional_id)
    profesional.calificacion_promedio = Decimal(promedio).quantize(Decimal("0.01")) ...

# al crear la reseña:
db.add(resena)
db.flush()                              # persiste la reseña ANTES de promediar
_recalcular_promedio_profesional(db, servicio.profesional_id)
db.commit()                             # reseña + promedio en una sola transacción
  • func.avg(...): el promedio lo calcula Postgres, no Python (más rápido y exacto).
  • flush vs commit: flush manda el INSERT a la base (para que el AVG la cuente) pero dentro de la transacción; commit confirma todo junto. Si algo falla, se revierte la reseña y el promedio juntos: atomicidad.

«¿Diferencia entre flush y commit?»
flush sincroniza los cambios pendientes con la base (ejecuta el SQL) pero no cierra la transacción; los cambios todavía se pueden hacer rollback. commit hace flush y además confirma la transacción de forma permanente.

5. Alembic — migraciones

¿Qué es una migración? El esquema de la base cambia con el tiempo (nueva columna, nueva tabla). Una migración es un archivo versionado con upgrade() (aplicar el cambio) y downgrade() (revertirlo). Alembic es "git para el esquema": cada migración encadena con la anterior y la base recuerda en qué versión está.

El flujo diario son dos comandos:

flujo de Alembic
# 1) cambiás un modelo y autogenerás la migración comparando modelos vs base:
alembic revision --autogenerate -m "agregar telefono a usuarios"
# 2) la aplicás:
alembic upgrade head      # head = la última versión
  • env.py lee settings.DATABASE_URL (no se hardcodea) e importa Base.metadata (por eso cada modelo debe importarse en models/__init__.py: si no, Alembic no lo "ve").
  • local vs prod: en local alcanzaba create_all; en prod siempre Alembic, porque preserva los datos y es reversible.

Siempre revisá el autogenerate. Detecta muy bien tablas y columnas nuevas, pero un rename lo ve como "borrar + crear" (perderías datos). Leé el archivo generado antes de aplicarlo.

6. Tests con pytest

30 tests cubren cada vertical. La clave está en el conftest.py: una base SQLite en memoria y un override de get_db, así los tests no necesitan Postgres y corren en segundos.

backend/tests/conftest.py (extracto)
engine = create_engine("sqlite://", connect_args={"check_same_thread": False},
                       poolclass=StaticPool)  # 1 sola conexión en memoria

@pytest.fixture
def client(db):
    def override_get_db():
        yield db
    app.dependency_overrides[get_db] = override_get_db   # inyecta la DB de test
    with TestClient(app) as c:
        yield c
  • Override de dependencias: app.dependency_overrides reemplaza get_db por uno que usa la base de test. Toda la app, sin tocar su código, ahora habla con SQLite. Es la razón de usar DI.
  • Aislamiento: el esquema se crea y se borra por test, así cada uno parte de cero.
  • Truco real: el conftest setea ENVIRONMENT=test antes de importar la app para que el lifespan no intente tocar Postgres con create_all.
un test de extremo a extremo

Repaso de entrevista

«¿Por qué separar schemas de modelos?»
Para desacoplar la representación interna (tabla) del contrato público (API): validás la entrada, controlás exactamente qué sale (sin filtrar campos sensibles) y podés versionar la API sin tocar la base.

«¿Cómo testeás sin levantar Postgres?»
SQLite en memoria + override de la dependencia get_db. Gracias a la inyección de dependencias, reemplazo la sesión real por una de test sin tocar el código de la app.

«¿Cómo garantizás consistencia al crear una reseña?»
La reseña y el recálculo del promedio del profesional van en la misma transacción (flush + commit). Si una falla, se revierten ambas: atomicidad.
